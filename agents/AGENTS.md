# Agent Behavior Rules

## Conversation

1. ユーザーへの返答には日本語を使う。
2. Bash ツールを呼び出すときは必ず `description` パラメータに日本語でコマンドの目的を書く。省略禁止。
3. 表やユーザーへの確認事項には番号を付け、ユーザーが番号だけで回答できるようにする。

## Coding

1. 差分を小さくする
   1. 与えられたタスクを段階的に進める計画を立て、各段階の差分が小さくなるようにする
   2. ファイルやディレクトリの改名・移動は先に行い、先に commit してからファイルを編集する
   3. 既存のコードを活用し、目的達成のための編集は最小限にする（似たような責務のコードを再作成したり、タスクの本質とは関係ない改修を勝手に行わない）
2. 未定義のものを使わない。新たにオブジェクトや関数を追加するときは先に定義してから、利用箇所で呼び出す。未定義のまま、先に利用箇所を実装するのは禁止。
3. コードを数行読めばわかるようなことはコメントはしない。設計理由など、コードを読んだだけじゃわからない場合のみコメントする。
4. `git` コマンドはカレントディレクトリが対象リポジトリであれば `-C` を付けない
5. 参照されなくなったファイルに気づいたら、そのPRでまとめて削除する
6. 想定どおりに動かないときは、仮説で対策を重ねる前に、想定した経路（どの分岐・どのクラスが選ばれたか）を最初にログ等で確認する

## Security

1. Secret Manager などパスワード・シークレットを取得するコマンドは直接実行しない。必ず環境変数に格納するコマンドを提示する。
   1. 良い例: `export PASSWORD=$(gcloud secrets versions access latest --secret=xxx)`
   2. 悪い例: `gcloud secrets versions access latest --secret=xxx`（値がターミナルに表示される）
2. パッケージマネージャー・ランタイムでライブラリや CLI ツール等をインストール・更新する前に、インストール対象と、それを動かす基盤（パッケージマネージャやランタイムなど）について、直近に見つかった・話題になっている脆弱性を調べる（公式のセキュリティ情報を優先）。
   1. 調べた内容は、選ぶバージョンの案とあわせてユーザーに簡潔に提案する。バージョンはユーザーに確認してから決める（勝手に上げない）。
   2. 案は最新だけでなく、現状の環境・依存との互換性を考慮して複数出してよい。各案について、調べた脆弱性が対策済みかどうかを併記する。
   3. パッケージマネージャ・ランタイムの例: `uv` / `pip` / `pipx` / `npm` / `npx` / `bun` / `brew` / `cargo` / `go` / `gem` / `mise` / `nvm` / `pyenv` / `asdf`

## Document Reading

1. 機械が読みにくい形式（HTML・PDF等）のドキュメントがあれば、調査の前に Markdown に変換する。

## Web Request

1. GitHub の URL が与えられた場合、 `gh` コマンドを使ってソースコードを探索・参照する。
2. 外部 API を大量に叩く前に、リクエスト数・quota・料金の見積もりを簡潔にユーザーに提示し、許可を得てから実行する。quota や料金は都度最新情報を調べる。
3. 原則として、なるべく無料枠〜少額に収まるようリクエストプランを提案する。
4. Notion への書き込みなど、レート制限が存在する処理は、制限にかからない範囲で上限いっぱいまで並列化等で高速化する。
